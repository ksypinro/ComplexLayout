The 58-Point Band

After a portrait → landscape rotation on iPad, tab 3's paged content stops 58 pt short of the display bottom. Across 451 captured views, exactly two values change — and their arithmetic accounts for the symptom to half a point. The reverse rotation is clean, so the defect belongs to one direction only. Three attempts to fix it in place were measured failing; the fix that works replaces the pager.

Measured by decoding the raw framebuffer column at x = 200.

The band renders pure white, 255,255,255 — not systemGroupedBackground (242,242,247), which is what MosaicViewController paints on its own view. The mosaic view is therefore absent from that region rather than showing its own background, which rules out every background-colour explanation and points at geometry.

The defect is directional. Landscape → portrait re-laid out correctly and chose the full 1180. Only portrait → landscape chooses the safe-inset height. The safe-area insets are T96 B20 in both orientations, so 96 + 20 = 116 is the constant being subtracted — 1180 − 116 = 1064 in portrait, which is not what portrait used, against 820 − 116 = 704 in landscape, which is.

It is deterministic and not tied to a landscape variant. The defect reproduced across two separate processes and both landscape orientations — LandscapeRight (4) and LandscapeLeft (3) — producing byte-identical results each time: contentSize 704, cell y = −58, band boundary 762.0.

06 The delta

Two values change across 451 nodes. Nothing else does.

PagingCollectionView
.contentSize.height 820→704
UIKitPagingCell
.frame.origin.y 0→−58

No frame size changes anywhere. No constraint changes. layout.ambiguous is false on all 451 nodes. Every view in the suspect chain has translatesAutoresizingMaskIntoConstraints = true and owns zero constraints — the only constrained view is the mosaic collection view, whose 8 constraints are identical in both captures and are internal supplementary-view sizing. There is nothing constraint-shaped to fix.

07 Mechanism

A full-height cell centred inside a safe-area-height content box.

820 − 96 − 20  =  704   height − safeArea.top − safeArea.bottom = new contentSize.height
(704 − 820) ÷ 2  =  −58   cell centred in content → observed frame.origin.y
−58 + 820  =  762   cell bottom edge = measured start of the white band

On re-layout after rotation, PagingCollectionView derives its content height from the safe-area-inset height (704) instead of its full bounds height (820). Its page cell is still 820 tall, because CustomPageView declares .ignoresSafeArea() and therefore genuinely is full-height. The paging layout centres the cell within the content height, so the 116 pt surplus splits evenly above and below.

Everything below the cell — the hosting views, MosaicViewController.view, and the mosaic collection view — has a correct frame of (0,0) 1180×820 relative to its own parent and is simply carried along. That is why their frame reads correct while screenFrame reads −58.

The cell's safeAreaInsets.bottom falling from 20 to 0 is a consequence, not a cause: once the cell's bottom edge at 762 sits above the window's safe-area boundary at 800, UIKit correctly reports no bottom inset for it.

08 Initial reasoning

A size contract that only the rotation re-layout path breaks.

The fresh-launch path sizes paging content to the full height (820), which matches the cell, so the cell sits at 0 and the layout is correct. The rotation re-layout path sizes it to the safe-area height (704), which no longer matches the 820 pt cell — and the centring rule converts that size disagreement into a position error.

The application-side ingredient is the pair of .ignoresSafeArea() calls added for the edge-to-edge requirement: one on the TabView in CustomView, one on the page in CustomPageView. These make the page legitimately full-height, which is exactly the condition under which a safe-area-height content box misaligns. Without them the cell would be 704 pt tall and would agree with the recomputed content height.

The directional evidence sharpens this. Portrait re-layout picks the full height and is correct, so the paging container is not simply "wrong after any rotation" — something specific to the portrait → landscape transition selects the inset height. Whether that is the shrinking height, the orientation itself, or the order in which size and safe area are applied is not observable from outside SwiftUI; what is established is that the choice differs by direction and that the wrong choice is exactly the safe-inset height.

Corroborating that this is a paging-container re-layout weakness rather than anything downstream: the off-screen page is still 820 × 1180, full portrait geometry, and carries an 820 × 1180 mosaic collection view inside it.

09 Explicitly exonerated

The inset plumbing is behaving correctly.

The mosaic collection view's own state is byte-identical before and after

contentInset T216 B20 · adjustedContentInset T216 B20 · contentOffset (0, −216) · contentSize 1180 × 1247.25

216 = 96 + 120 is precisely the safeAreaInsets.top + reservedHeight that OverviewView computes. The contentInsetOverride plumbing, the GeometryReader, and reservedHeight are all correct and are not implicated. The scroll view is perfectly configured and is simply being carried 58 pt too high by its ancestor.

11 What was tried, and why each failed

Three attempts to keep the pager. Each was measured rather than assumed.

All three aimed at the same thing: stop the paging view receiving a safe area to subtract
AttemptMechanismMeasuredWhy it failed
1st Try UIHostingController
.safeAreaRegions = []		 Paging view still T96 B20; contentSize 3540×704; cell at y = −58 Governs SwiftUI's own layout system only. The paging view is a UIKit collection view reading the UIView chain, which the flag never touches.
Fix 2a Container view controller setting negative additionalSafeAreaInsets on the hosting controller Hosting view T96 B20 — identical to its parent, as if nothing had been set UIKit only adds with that property. Negative values are ignored, so it cannot subtract an inherited inset.
Fix 2b Overriding safeAreaInsets on the container's own view to return zero Container reports T0 B0; its child hosting view still reports T96 B20 The override changes what that view reports to callers. It does not change what UIKit propagates.

Fix 2b is the conclusive measurement, because of a detail in its numbers: the container's wrapper reports T32, but the child hosting controller receives T96. The tab bar's 64 pt is not inherited down the view tree — UIKit computes the safe area per view controller and applies it to each one directly.

That closes the search. No parent view and no parent controller can withhold the safe area from a child hosting controller, and additionalSafeAreaInsets — the only supported lever — cannot subtract. Two further options were rejected by analysis rather than experiment: confining the TabView inside the safe area makes the two heights agree but leaves content 96 pt short at the top, failing AC-1 outright; and enlarging the pager's frame does not help, because the cell height tracks the bounds, so the mismatch simply follows.

So TabView(.page) can satisfy either "content reaches the physical edges" or "survives rotation" — not both, through public API.

12 The fix

Replace the pager, so there is only one height in play.

Paging becomes ScrollView(.horizontal) + LazyHStack + .scrollTargetBehavior(.paging), with .scrollPosition(id:) bound to the selection in both directions so swipe and header-tap stay in step. Each page's size is set explicitly from the container — .frame(width: proxy.size.width, height: proxy.size.height) — so there is no second, independently derived content height that can drift away from it.

The trade-off, stated plainly. This replaces the pager, which was the change we were trying hardest to avoid. Paging, page identity and scroll position all now work differently. Against that: the three in-place attempts are not near-misses, they are measured dead ends, and the structural reason they fail is not going to change.

One incidental improvement shows up in the capture. The TabView kept a stale 820×1180 portrait page alive after rotation, with a full portrait mosaic collection view inside it. LazyHStack instantiates only the visible page — the post-fix capture holds a single page host and a single mosaic collection view.

All four implementations are kept side by side in the project as switchable specimens — CustomView_Issue, CustomView_1stTry, CustomView_Fix2 and CustomView_Fix1 — each documented with what was measured rather than what was hoped, so the dead ends do not get re-explored.

13 Method and evidence gaps

Stated plainly, so the conclusions can be weighed.

  • Why SwiftUI derives 704 is not directly observable. That computation lives inside SwiftUI's paging layout, which this provider cannot see: no logical SwiftUI tree, no private layout internals. What is established is the value, its exact arithmetic relationship to the symptom, and that no application-owned property changed.
  • No cold-launch portrait capture. Portrait was captured by rotating into it, which is the state the defect actually starts from. A cold launch straight into portrait would additionally separate "landscape re-layout is special" from "any re-layout to a shorter height is special" — a refinement of the mechanism, not a challenge to it.
  • Model-layer geometry, not presentation layer. Occlusion and ancestor clipping are not established by this provider; getters may run application code; text and accessibility labels are intentionally omitted from the capture.
  • Hierarchy evidence outranked pixel evidence once. A framebuffer probe using a fixed rotation correction read the wrong screen edge under LandscapeLeft and briefly suggested a clean layout; the captured hierarchy contradicted it and was right. Raw simulator buffers are always portrait-shaped — the orientation enum has to be applied, not a constant.
  • The fix is verified on one device and one trigger. iPad Air 11-inch, rotation only. The working implementation has not been re-checked on iPhone since the pager was swapped, and Split View / Stage Manager resizing stayed out of scope by decision — the same class of re-layout trigger, so worth testing before relying on it there.
  • Pointer identity is meaningful where it is used. The portrait and post-rotation landscape captures come from PID 57665 with no relaunch between them, so that comparison is object-level rather than heuristically matched.
